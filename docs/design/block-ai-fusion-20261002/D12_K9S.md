# D12：k9s 原生终端与输入交接验收

2026-10-03，`composer` 工作区；macOS 27.0.1（26A434），实际 k9s 0.50.16。生产 Trail UI、原生 PTY 和 k9s 均实际运行；Kubernetes API 与 AI 回复由隔离的本机 HTTP fixture 提供。这是终端交互验收，不是真实集群或模型质量评测，也没有使用用户的 kubeconfig。

## 发现并修复的菜单问题

第二次运行 k9s 后用终端 Ctrl+C 退出，shell 已恢复，但立即打开的 tab 右键菜单仍提示“当前应用需要使用普通终端”。菜单在打开时固定了 `TerminalModeState`，没有订阅之后的能力变化；因此等多久都不会更新，必须关闭重开。

桌面模式菜单现在在弹出路由内订阅对应 session 的模式状态。已打开的菜单会随能力恢复而启用 Blocks，也会在能力再次丢失时禁用；重检入口同样跟随退出／只读状态。恢复不会自动切换模式，也不会写 PTY。手机菜单已有这种订阅机制，保持原有行为。

新增组件回归保持同一个菜单打开，验证 suspended→ready→suspended→ready，再手动选择 Blocks；没有终端输入或会话关闭。原始用例在修复前明确失败于“恢复后仍 disabled”，见[失败日志](evidence/k9s/k9s-menu-before.log)。修复后的用例包含在 [840 项应用回归](evidence/k9s/k9s-app-regression.log)中。

## 真实 k9s 流程

1. 从 Blocks 启动 `k9s --readonly --splashless -c pods`，实际显示合成 Pod 列表。进入 alternate screen 和鼠标报告后，撤走 Blocks／Composer，占用 **1728×1002px** 可用终端；按实际字体单元计算并核对 **44 行 × 203 列**。
2. 用终端文本输入打开 k9s 帮助页。打开 AI 覆盖页后，底层 viewport 尺寸与 PTY 行列均不变；输入未发送草稿。
3. AI 输入框内 Ctrl+C 不写任何 PTY 字节。第一次 Esc 只关闭 AI，k9s 帮助页逐字符保持、草稿保留；第二次 Esc 才写入 `27` 并回到 Pod 列表。
4. 再次打开 AI，审阅 `ESC`、文本 `:q`、`ENTER`。批准之前 TUI 仍运行、网格不变；批准后精确写入 `[27, 58, 113, 13]` 一次，关闭覆盖页并退出 k9s，退出码 0。
5. 保持 Normal，经 tab 右键手动恢复 Blocks。恢复动作没有 PTY 输入。
6. 再启动一次 k9s，终端拥有焦点时 Ctrl+C 实际发送 `03` 并退出；同一会话再次手动恢复 Blocks。最终保留两条独立原生执行记录，退出码均为 0。
