# D05 回复结束后的输入焦点

2026-10-03，`composer` 工作区。补齐 [D05 结果与继续追问](DESIGN.md#d05-结果证据与继续追问) 在上一轮 [真实模型验收](MODEL_SCENARIOS.md) 中尚缺的直接交互证据。保持手机固定字号，只使用生产组件模拟，不测试 iPhone 真机。

## 问题与修复

键盘通过 Tab 到达“执行一次”，按 Enter 批准后，审批按钮会离开组件树。Flutter 把焦点退回之前 Tab 经过的正文选择区域；回复结束时也没有明确的恢复逻辑。结果可见，但不能直接续问。[修复前日志](evidence/focus/focus-before.log)中，桌面续问用例的 `inputFocus.hasFocus` 为 false；另五个阅读、选区、设置、手机和后台保护用例通过。

现在桌面提交后先将原审批按钮的键盘归属交给任务视图。当前任务收到最终正文回复、仍跟随最新内容，且没有转去其他操作时，再把焦点交回 AI 输入框。回复只是结束当前推理，不会把任务目标标成已完成，也不会因为恢复焦点而发送草稿或输入终端。

焦点恢复在下一帧执行，重新检查任务 ID、回复 ID、阶段和当前页面，避免旧回复覆盖新任务。用户回看历史、点击时间线开始选择、Tab 到其他控件、打开弹窗、离开应用或进入全屏终端时保留其输入归属。手机保持当前键盘状态：审阅后已收起的键盘不因回复出现而弹出；用户已经在续写时，草稿、选区和中文组词保持原值。

这些是 D05“不抢走用户阅读位置”的具体处理；任务切换、审批条件、命令执行次数和 PTY 网格没有改动。

## 直接验证

新增 `example/test/ai/terminal_ai_focus_test.dart` 的 11 项交互回归：

- 桌面键盘批准后，不点击输入框即可直接续写同一任务；不会额外请求模型或执行命令。
- 单纯通过键盘发送问题，无终端命令时也恢复输入。
- 历史阅读的原消息锚点、40px 偏移和键盘拥有者保持。
- 点击并选择已有助手正文后，新回复不清除选区或抢走焦点。
- 设置弹窗内的编辑焦点与任务栏其他控件的 Tab 焦点保持。
- 后台完成不抢焦点，回前台不补做迟到的自动聚焦。
- 旧任务的迟到回复不进入新任务、不覆盖新草稿或焦点。
- 手机审阅后不重新打开键盘；手机与桌面的续写文本、选区和中文 composing 范围逐值保持。

上述 11 项与既有 54 项工作区测试一起 [65 项通过](evidence/focus/focus-after.log)。选区测试先通过真实点击取得文本区域，再选择内容；没有依赖 Tab 残留的偶然焦点。

原生验收在 macOS 27.0.1（26A434）运行生产 HTTP 客户端与实际本地 PTY。批准编辑后的命令、获取原生回执和结果解释后，测试等待 AI 输入框真正持有焦点，再直接通过文本输入通道写入 `Keep this unsent follow-up`，中间没有点击或调用 `enterText` 强制聚焦。接着打开和关闭证据阅读器，草稿仍保留。
