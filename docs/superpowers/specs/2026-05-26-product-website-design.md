# 产品官网设计

## 背景

这份设计定义 `flutterm` 第一版产品官网。官网服务的是“想了解、关注或开源试用一个桌面终端 app”的用户，而不是只面向 package 使用者或内部开发者。

仓库当前事实：

- `flutterm` 是 Flutter/Dart workspace。
- `packages/flutterm_pty` 负责 PTY 会话传输和 FFI 包装。
- `packages/flutterm_terminal` 负责 session runtime、viewport、输入、选区和滚动适配。
- `example/` 是可运行的 macOS demo app，包含 tab、窗口壳、菜单、profile/defaults 和集成 smoke。
- `native/core` 负责 Rust PTY、VT 解析、frame diff 和事件输出。
- macOS 本地 shell 主链路当前最成熟。跨平台桌面体验是产品方向，但不能在官网里写成已经完成。

## 目标

- 建立清楚、有记忆点的产品印象：干净、稳定、有原生感的跨平台桌面终端。
- 首屏有开发者工具的鲜明气质，深色 Carbon Neon 是主品牌视觉。
- 用强技术证明让开发者相信产品不是空壳。
- 让用户知道当前最可靠的试用路径是开源源码和本地运行 example。
- 诚实表达平台状态：macOS 当前最成熟，其他桌面平台在路线图中推进。
- 支持深浅两色切换，深色表达品牌，浅色保证白天阅读和日常浏览体验。

## 非目标

- 不承诺正式下载包。
- 不把官网写成“全平台已经可用”。
- 不直接暴露内部 M1-M5、任务编号或验证阻塞文档作为用户页面结构。
- 不做文档站替代品。
- 不做登录、订阅、付费、云同步或遥测。
- 不扩展产品能力，只设计官网表达和静态展示结构。

## 受众和主张

主要受众：

- 想了解一个桌面终端 app 的开发者和桌面用户。

次要受众：

- 会看源码、验证工程质量、判断项目是否值得关注的技术用户。

核心记忆点：

> 一个干净、稳定、有原生感的跨平台桌面终端。当前 macOS 体验最成熟，未来走向更多桌面平台。

主 CTA：

- `查看源码`

次 CTA：

- `了解技术实现`
- `本地运行示例`

不使用 `立即下载` 作为第一版主 CTA。

## 站点结构

第一版是静态小型产品站，中文为主。导航保持短：

- `功能`
- `技术`
- `路线图`
- `开源试用`
- `GitHub`

页面：

1. 首页 `/`
   - 建立第一印象。
   - 黑底高对比，霓虹状态色，强文案，动态终端感。
   - 明确 macOS 当前最成熟，同时保留跨平台桌面目标。
2. 功能 `/features`
   - 面向用户体验讲产品。
   - 不按代码模块组织。
3. 技术 `/technology`
   - 放强证明。
   - 解释 Flutter UI、PTY/FFI、Rust native core、VT/xterm 对齐和验证覆盖。
4. 路线图 `/roadmap`
   - 用“现在可用 / 接下来 / 未来”表达。
   - 不把内部任务编号作为官网结构。
5. 开源试用 `/open-source`
   - 引导用户查看源码、运行 example、阅读验证说明。
   - 说明当前不是正式下载页。

副文案：

```text
flutterm 是一个面向本地开发工作流的开源终端实验。当前 macOS 体验最成熟，目标是走向更完整的跨平台桌面终端。
```

小标签：

- `macOS ready`
- `Flutter built`

- `Open source`

CTA：

- 主按钮：`查看源码`
- 次按钮：`了解技术实现`

右侧主视觉：

- 使用动态终端窗口，而不是单纯静态截图。
- 无依赖 CSS/JS 动画循环显示少量命令状态。
- 示例状态包含本地 shell 启动、resize、copy/paste、xterm probes、macOS ready、desktop platforms next。
- 终端窗口有细边框、轻微悬浮、深色面板和霓虹青绿状态文本。

首屏底部短证明：

- `本地 shell 主链路`
- `macOS 当前最成熟`

首页后续区块：

- 产品体验概览。

- 开源试用入口。
- 路线图预览。

## 功能页设计

功能页按用户体验组织。

### 本地 shell，不绕路

说明本地会话和常见开发命令可以直接运行。文案强调“本地开发工作流”，不展开 FFI 细节。

### 清楚的桌面工作区

说明 tab、窗口壳、profile、defaults、空状态和焦点管理。重点是用户能清楚知道当前操作对象。

### 终端交互基础扎实

说明复制、粘贴、滚动、resize、选区、退出后的恢复路径。这些是桌面终端日常使用的基础。

### 有个性，但不吵

说明视觉气质：高对比、紧凑、状态清楚。页面可以有态度，但功能页不能每段都像广告语。

## 技术页设计

技术页给强证明，但不堆黑话。

### Flutter 负责界面，native core 负责终端底层

用简图说明：

```text
UI shell -> flutterm_terminal -> flutterm_pty -> Rust native core
```

每层只写职责：

- UI shell：窗口壳、tab、菜单、profile/defaults。
- `flutterm_terminal`：session runtime、viewport、输入、选区、滚动。
- `flutterm_pty`：PTY 会话传输和 FFI 包装。
- Rust native core：PTY、VT 解析、frame diff 和事件。

### 分层清楚，方便验证

说明 PTY、viewport、输入和选区各自有边界。用户不需要读源码也能理解“哪层负责什么”。

### 向 xterm 行为靠齐

说明项目通过 probe、回归测试和手工验证队列持续靠齐终端行为。措辞使用“靠齐”和“验证”，不写“完全兼容”。

### 验证不是装饰

放一个短矩阵：

| 类型 | 目的 |
| --- | --- |
| Flutter tests | 验证 UI、session 和交互行为 |
| Dart tests | 验证 package 逻辑和边界 |
| Rust tests | 验证 native core 行为 |
| macOS manual smoke | 验证桌面真实交互 |
| performance baseline | 观察终端输出和渲染表现 |

技术页底部放“来自仓库的证据”：

- `README.md`
- `docs/ARCHITECTURE.md`
- `docs/TESTING.md`
- `docs/ROADMAP.md`
- GitHub 仓库链接

## 路线图页设计

路线图面向用户，不暴露内部任务编号。

### 现在可用

- macOS 本地 shell 主链路。
- tab 和窗口壳。
- 复制、粘贴、滚动、resize。
- 基础 profile/defaults。
- 可运行的验证入口。

### 接下来

- 终端一致性补强。
- 手工、平台和性能证据收口。
- runtime 扩展基座。
- 更多本地开发工作流能力。

### 未来

- 更多桌面平台。
- 更完整的 workspace 能力。
- 更清楚的平台状态和验证证据。

路线图每条都要能看出状态。已经可用、正在推进、未来方向不能混在同一句里。

## 开源试用页设计

开源试用页不写成正式下载页。

主要模块：

1. 查看源码
   - GitHub 主入口。
2. 本地运行
   - 最短路径：

```bash
dart pub get
cd example
flutter run -d macos
```

3. 验证方式
   - 链接到测试文档。
   - 简短解释可以运行哪些测试。
4. 平台状态
   - macOS 当前最成熟。
   - 其他桌面平台在路线图中推进。

## 视觉系统

### 主题模式

全站支持深浅两色切换。

默认行为：

- 首次进入跟随系统深浅色。
- 页头保留可见主题切换按钮。
- 用户选择后用本地存储保存。

深色主题：Carbon Neon

- 近黑背景。
- 霓虹青绿主状态色。
- 冷蓝紫作为辅助提示色。
- 深色终端窗口和细边框。
- 首页在深色下最有品牌冲击力。

浅色主题：Neon Paper

- 浅纸面背景，不使用纯白大面积营销页观感。
- 仍保留深色终端窗口。
- 使用同一套青绿状态色。
- 对比足够，适合白天阅读。

### 组件规则

- 小圆角，细边框，紧凑间距。
- 主要按钮清楚，次级按钮克制。
- 不使用大面积紫蓝渐变作为背景。
- 不用装饰性光球或模糊色块。
- 首页可以强表达，内容页更克制。
- 关键主张旁边要有状态说明或可点击证据。

### 文案规则

- 中文为主。
- 产品名和必要技术名可以保留英文。
- 避免术语堆叠。
- 不写过度承诺。
- 不把内部项目管理语言直接搬给用户。

## 静态站架构

第一版用静态展示站即可。技术栈在后续实现计划中再定，但设计需要满足：

- 有真实路由或可直接访问的静态页面。
- 公共 header、footer、theme toggle、CTA、proof card、terminal hero、page section 组件可复用。
- 页面内容可以硬编码在源码中，不需要 CMS。
- 外部链接集中维护，避免页面里到处散落 GitHub URL。
- 无网络请求也能展示主体内容。

## 数据和状态

需要的状态很少：

- 主题选择：`system`、`dark`、`light`。
- 用户选择保存到本地存储。
- 初次访问根据 `prefers-color-scheme` 决定默认显示。

不需要：

- 用户账号。
- 表单提交。
- 订阅邮箱。
- 下载统计。
- 远程配置。

## 错误和降级

- 如果 JavaScript 不可用，页面默认展示系统主题或深色主题，主体内容仍可读。
- 如果本地存储不可用，主题切换只在当前页面生效。
- 如果外部 GitHub 链接不可访问，页面仍保留运行命令和说明。
- 如果动画被用户系统设置降低，终端主视觉应停止循环或使用非常轻的状态切换。
- 所有页面在没有真实下载包时都不能展示“立即下载”。

## 测试和验收

实现完成后至少验证：

- 首页、功能、技术、路线图、开源试用页面都能直接打开。
- 导航和 CTA 链接正确。
- 深色、浅色、跟随系统三种主题行为正确。
- 主题选择可以保存，刷新后保持。
- 移动宽度和桌面宽度无文本重叠、按钮溢出或横向滚动。
- 终端主视觉不会遮挡文案。
- `prefers-reduced-motion` 下动画降级。
- 关键图片或视觉元素缺失时页面仍能表达产品。
- 页面文案没有把未来能力写成当前能力。

## 实施边界

第一版只需要把官网静态站做出来。可以先使用硬编码内容和少量轻量脚本。后续如果需要继续维护更多内容，再考虑更完整的内容组织或文档站能力。
