# flutterm Acceptance

这份文档定义全局完成标准。后续每个任务文档都应引用它，而不是各自发明一套“完成”的含义。

## 全局完成定义

一个任务只有在以下条件同时满足时，才算完成：

- 目标落在任务 `Scope` 内，没有扩展到 `Non-goals`
- 相关代码能正常构建或运行
- 相关自动化检查通过
- 没有新增 analyzer / lint / format 问题
- 相关文档已经同步更新
- 手工验收已执行，或明确说明为什么本次不适用

## 必填任务字段

每个任务文档至少应包含这些区块：

- `Goal`
- `Scope`
- `Non-goals`
- `Files In Scope`
- `Functional Acceptance`
- `Verification Commands`
- `Manual QA`
- `Done When`
- `Risks / Follow-ups`

## 任务级验收规则

### Goal

- 只允许一个清晰目标
- 目标必须可验证，不能写成抽象口号

### Scope

- 只写本次允许修改的能力和模块
- 范围越小越好，优先单一问题单一任务

### Non-goals

- 明确排除容易被顺手做掉的扩展项
- 如果实现过程中发现值得顺手做的内容，转成新任务，不在当前任务里偷带

### Files In Scope

- 明确允许修改的目录或文件
- 如果最终修改超出范围，必须解释原因

### Functional Acceptance

- 只写从用户视角看得见的行为结果
- 每一条都必须能被命令、测试或人工步骤验证

### Verification Commands

- 必须写可以直接执行的命令
- 命令应尽量最小化，但要足以覆盖变更风险
- 如果没有执行某个命令，最终说明里必须写原因

### Manual QA

- GUI、terminal、输入法、滚动、复制粘贴这类能力默认需要人工检查
- “没有时间手测” 不能作为跳过理由

### Done When

- 用一句话或几条规则重述任务的关闭条件
- 不能只写“代码合并后”

## 标准失败处理

出现以下任一情况时，任务不能标记完成：

- 验证命令失败
- 手工验收失败
- 行为实现与 `Functional Acceptance` 不一致
- 修改超出 `Scope` 且没有记录
- 存在明显已知问题但没有写入 `KNOWN_ISSUES.md` 或任务文档

## 结果汇报格式

每次任务完成后的总结建议固定为：

- `变更`
- `验证`
- `剩余风险`

这样可以让 `oh my codex` 的输出长期保持一致，也方便后续回看。

## 文档更新规则

出现以下情况时，必须同步改文档：

- 模块边界变化
- FFI 契约变化
- 测试入口变化
- 当前范围变化
- 已知问题新增或关闭

文档更新优先级：

1. `tasks/` 当前任务文档
2. `TESTING.md`
3. `KNOWN_ISSUES.md`
4. `ARCHITECTURE.md`
5. `ROADMAP.md`
